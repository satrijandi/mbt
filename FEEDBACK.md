# FEEDBACK: senior MLOps and data science review of mbt

## Review 2 - fresh review of current `main` (2026-07-20)

Review date: 2026-07-20, against `main` (a4c2230).
Perspective: a senior MLOps engineer and a senior data scientist re-evaluating the repo after Review 1 (below) closed on 2026-07-07.
Method: four parallel deep reads (core engine + CLI, all adapters, DS methodology, ops/CI/DX), each cross-checked against Review 1's progress log so nothing already fixed or deliberately deferred is re-litigated as new.
Every finding has file evidence and is scored on impact (from a DS or MLOps-engineer lens) and effort (S = hours, M = days, L = weeks).
The fast suite is green at review time (`870 passed, 45 skipped`), mypy/ruff/mkdocs clean, so this is a review of gaps and risk, not of a broken tree.

The headline has not changed since Review 1: mbt is an unusually well-engineered v0.1, and the remaining problems have moved to the edges.
Three edges dominate now.
First, delivery: the tool is not actually installable and the CI it stamps into every new project is dead on arrival, so the flagship loop cannot run for a real first user.
Second, the warehouse serving leg is only half-built: a Snowflake or Spark team can train, gate, and promote in-warehouse but cannot score or monitor back into it, which is the one thing a "dbt for ML" is supposed to guarantee.
Third, production resilience and DS depth: no retry on external I/O, non-atomic control-file writes, a shift monitor with a single on/off threshold, and a regression vertical that ships in code but is demonstrated nowhere.

### Priority x effort map

| | Low effort (S) | Higher effort (M / L) |
|---|---|---|
| **High impact** | **Do first:** R2-1 release tag + publish gate, R2-3 atomic writes, R2-14 drop dead `otel` extra, R2-16 `s3_wide` test | **Big bets:** R2-2 retry/backoff, R2-17 warehouse scoring sink, R2-7 cross-validation, R2-8 calibration step, R2-10 pinned-manifest scoring |
| **Lower impact** | **Fill-ins:** R2-19 `scored_at` guard, R2-20 month/year windows, ECE equal-frequency bins, MLflow archive-on-promote, H2O `load()` columns | **Reconsider scope:** slim the 19-service showcase, first-class `mbt rollback` tooling, multiclass/ranking/survival verticals |

### The three I would fix before any wider adoption

1. **Make the tool installable and the scaffold CI runnable (R2-1).** One tag + one publish-gate, and the whole PR -> CI -> registry loop the project sells starts working for new users. Highest impact-to-effort ratio in the repo.
2. **Close the warehouse serving leg (R2-17).** Snowflake/Spark are the target audience; today they hit a hard `ConfigError` at `mbt score`, and even the "done" Snowflake path writes predictions to local disk, not the warehouse.
3. **Add production resilience: retry/backoff (R2-2) and atomic control-file writes (R2-3).** The two most common ways a scheduled cloud pipeline fails transiently, and mbt currently has no defense against either.

## P1 - fix before wider adoption

### R2-1 Release readiness is broken at the user edge (two coupled defects) [MLOps · S + S]

`git tag -l` is empty and nothing is on PyPI, yet `cli/scaffold.py` stamps `__MBT_VERSION__` -> `0.1.0` into every `mbt init` project's `requirements.txt`, which pins `mbt-core @ git+https://github.com/satrijandi/mbt@v0.1.0` (`_scaffold/requirements.txt:14-16`).
The first step of a fresh project's first CI job is `pip install -r requirements.txt` (`_scaffold/.github/workflows/pr_check.yml`), so it fails immediately on a tag that does not exist.
Separately, `release.yml` has no `needs: [ci]`, runs no tests, and passes no `skip-existing` before `pypa/gh-action-pypi-publish` uploads all 10 packages (`.github/workflows/release.yml:19-37`).
These are one workstream: the moment a tag is cut to fix installability, the ungated publish fires, so tagging a red commit ships broken, immutable wheels for 10 packages.
Impact: the flagship loop cannot run for any new user, and the fix path is itself a footgun.
Fix: cut `v0.1.0`, and gate `release.yml` on CI + `skip-existing`. Sequence them together.

### R2-2 No retry/backoff on any external I/O [MLOps · M]

Repo-wide grep for `retry|backoff|tenacity` hits only the scaffold's `publish_state.sh`; core has none.
S3 (`storage.py:94,113,142`), registry `register`/`transition` (`runners.py:540-541`), tracking `resume`/`log` (`runners.py:573-576`), and the DuckDB read/COPY path all fail hard on first error.
Impact: a single S3 `503 SlowDown`, a registry sqlite lock, or a network blip during artifact upload fails the whole node after the GPU-hours of training are already spent, and there is no idempotent resume, so the run restarts from scratch.
This is the single most common transient cloud-pipeline failure mode, and mbt has zero resilience to it.
Fix: bounded retry-with-jitter around the external-I/O seams (they are already centralized).

### R2-3 Control-file writes are non-atomic [MLOps · S]

`manifest.py:168-170` and `run_results.py:120-122` both `path.write_text(...)` directly; core has no `os.replace`/temp-file pattern anywhere (the prediction store got `_SUCCESS` crash-safety, but the two most-read control files did not).
Impact: a killed `mbt run`, or a `mbt docs generate` / `--state` read racing an in-progress write, observes truncated JSON, and every subsequent `--state`/`--manifest`/`docs` command then hard-fails with `invalid JSON in manifest` until the file is regenerated - a real CI flake vector where these commands run back-to-back.
Fix: write-temp-then-`os.replace` at both sinks.

## P2 - data-science methodology

### R2-4 Regression ships in code but is demonstrated nowhere [DS · M]

`TaskType.REGRESSION` is registered and compliance-tested (ADR-24), but every example, scaffold, tutorial, and golden model is `task: binary_classification`; no `.yml` in the repo sets `task: regression`.
Impact: a DS cannot copy a working regression project, cannot see which metrics/gates/monitors are valid for it, and must write the first one blind; the single most under-leveraged capability in the repo.
It also leaves regression + `ground_truth` monitoring and regression slice gates with no end-to-end exercise.
Fix: a regression example project plus one e2e, mirroring `churn_demo`.

### R2-5 The computed operating point is never applied or persisted to scoring [DS · M]

`threshold_at_precision_*`/`threshold_at_recall_*` are computed at evaluation (`metrics.py:121-148`), but `mbt score` writes raw probabilities (`ScoringOutputSpec`, `specs.py:707-715`) and no threshold is carried into the prediction store or applied.
Impact: Review 1 framed the operating point as "the deployable decision rule an outreach campaign consumes," yet downstream consumers get probabilities with no attached cutoff and must re-derive it out of band, defeating the purpose; there is also no decision-cost / utility framing (FP vs FN cost) to choose the point.
Fix: persist the chosen cutoff into the scoring output and optionally emit a thresholded decision column.

### R2-6 Shift monitoring is a single fixed threshold with no severity, significance, or multiple-testing awareness [DS · M]

`FeatureShiftSpec.threshold` is one float applied as `stat.value <= threshold` per feature (`quality/monitors.py:43-63`); KS is computed only at the 101 stored baseline quantiles (`monitoring.py:241-252`, an approximation of the true sup-gap) and compared to a fixed cutoff with no n-adjusted critical value.
Impact: unlike the leakage scan (which earned a two-tier warn/fail bar), shift monitoring is binary exit-2-or-nothing: no warn band, no top-k-shifted framing, no sample-size adjustment (over-fires on large nightly batches, under-fires on small ones), and a fixed PSI cutoff across many features generates false breaches from multiple comparisons.
There is also no trend accumulation (each run is independent) and no prior-probability / label-shift monitor.
Fix: severity tiers, an n-aware KS critical value, and a per-run "most-shifted features" summary.

### R2-7 No cross-validation, nested CV, or walk-forward backtest [DS · L]

Grep for `cross_val|kfold|walk-forward|nested|purged` is clean; `SplitSpec` models exactly one train/test/validation partition and tuning selects max-over-trials on a single validation carve (ADR-8).
Impact: optimistic-bias winner selection on small temporal test windows; the paired bootstrap defends the promotion decision but not the tuning selection, and time-series users have no purged/embargoed or expanding-window backtest at all.
This is the top remaining methodological gap for the small-data teams that are the common case.
Fix (L, roadmap-scale): an optional k-fold / walk-forward evaluation mode feeding the same gate engine.

### R2-8 No post-hoc calibration step, and `scale_pos_weight: auto` de-calibrates the very probabilities the demo measures [DS · L]

No isotonic/Platt/`CalibratedClassifier` exists anywhere; `ece`/`brier` are metrics only (`metrics.py:83-100`).
The demo sets `scale_pos_weight: "{{ auto }}"` and simultaneously measures `brier, ece` (`churn_classifier.yml:24,29`), so class-weight rebalancing inflates predicted probabilities and the model is miscalibrated by construction with no lever to fix it.
Impact: churn/retention interventions consume probabilities, not ranks, and today a bad `ece` has no remedy other than removing the imbalance weighting (which hurts ranking); the metric is diagnostic-only.
Fix (L): a recalibration artifact with champion/challenger calibration parity; interacts with R2-8-adjacent ECE binning (see P3).

### R2-9 Slice analysis has no binning for continuous columns, drops degenerate slices silently, and has no fairness/disparity primitive [DS · M]

`metrics.py:281-290` makes one slice per distinct value (no binning) and `continue`s past single-label slices with no note; `EvaluationSpec` has no `protected` concept and there is no disparity ratio, demographic-parity, or equalized-odds metric (self-acknowledged, `docs/mlops-alignment.md:90`).
Impact: slicing by any continuous column (age, tenure) explodes into hundreds of one-row slices and is unusable, confining slice analysis to low-cardinality categoricals; and for a tool that sells model specs as reviewable governance artifacts, the absence of a "gate the worst slice relative to the best" fairness primitive is a real hole.
Fix: quantile/user binning in slice specs, plus a relative-disparity metric and gate.

## P2 - MLOps and operations

### R2-10 `--manifest` reproducibility is unusable for the `score`/`monitor` commands you would actually schedule [MLOps · M]

Scoring nodes pin `snapshot_id` at compile (`compiler.py:152,383-393`) and `LocalDataAdapter._verify_snapshot` hard-errors when the live source differs (`data.py:169-186`), but `mbt score`/`mbt monitor` inputs (fresh unlabeled batches, arriving labels) are designed to change every run.
Impact: the ADR-19 pinned-manifest story cannot be applied to exactly the two commands you would run nightly, so a scheduled scorer must `compile` fresh each run rather than being driven from a reviewed, pinned manifest artifact; the `--manifest` flag is present and looks supported but hard-fails the moment new data arrives.
Fix: an "expected-mutable scoring window" exemption from snapshot verification. Recommend `/verify` end-to-end before acting.

### R2-11 Overlapping `mbt monitor` runs double-evaluate matured predictions [MLOps · M]

The ledger is read-then-write with no cross-process lock (`monitor.py:182,347`; `predictions.py:83-91` is a bare file write), so ADR-21's "evaluated exactly once" holds only within one process.
Impact: two overlapping monitor crons (a slow run still going when the next fires) both see the same run as unevaluated, both compute realized metrics, both fire ground-truth gates, both log a tracking point, and a breach double-alerts; overlapping schedules are the norm once label joins get slow.
Fix: atomic marker-create-if-absent or an advisory lock.

### R2-12 The scoring/monitoring vertical has no read surface [MLOps + DS · M]

`LocalPredictionStore.list_runs`/`read_marker` exist (`predictions.py:61,75`) but there is no `mbt` command to reach them; you cannot answer "what runs exist, which matured, which are evaluated, what was the coverage/realized AUC" without hand-reading JSON off disk.
Impact: the newest, most operationally-live part of the tool has zero observability into run/ledger state - a daily friction point for anyone running scheduled scoring.
Fix: a `mbt predictions ls/show` command over the existing store protocol.

### R2-13 The scaffold reference workflows are less hardened than the repo's own CI, and their "pinned" requirements are not pinned [MLOps · S-M]

The 7 shipped workflows have no `timeout-minutes` and no `concurrency` group (the exact hardening the repo added for itself in `ci.yml:10-12`), and use uncached `pip` + `setup-python` while the repo standardized on cached uv.
The `requirements.txt` the README calls "pinned" is 3 unhashed git refs with every transitive dep (xgboost, mlflow, numpy, pyarrow) floating (`_scaffold/requirements.txt:14-16`), even though `requirements.in` itself warns that a floating training environment invalidates the env digest.
Impact: users copy a weaker CI standard than the maintainers hold, and the reproducibility guarantee the whole `env_digest` story rests on is not delivered at the user edge (two retrains weeks apart can pull different xgboost/numpy).
Fix: add timeouts/concurrency/uv-cache to the scaffold workflows now (S); full transitive hash-pinning is blocked on PyPI (M, tied to R2-1).

### R2-14 No production observability export, and the `otel` extra is a dead install [MLOps · S to remove / L for real]

`mbt-core` declares `otel = ["opentelemetry-api>=1.24", "opentelemetry-sdk>=1.24"]` (`pyproject.toml:49`), but no source file imports `opentelemetry`; all production telemetry is example-side glue (`examples/showcase/.../push_metrics.py` parses `run_results.json` and PUTs to a Pushgateway).
Impact: real teams get no first-class metrics/tracing for production runs and must rebuild that bridge themselves, and `pip install mbt-core[otel]` installs libraries mbt never uses - a DX trap that also makes the `v0.1-status.md` "deferred" note read as contradicted.
Fix: remove the extra now (S); ship real OTel spans later (L). Related: events stream only to stderr with no durable `--log-file` sink, so capturing a machine-readable event timeline means scraping stderr.

### R2-15 No liveness / dead-man's-switch alerting on scheduled jobs [MLOps · M]

Every scheduled workflow alerts only `if: failure()` (`scheduled_retrain.yml:27`, etc.); there is no heartbeat or "expected run did not happen" signal.
Impact: the classic silent-failure mode - GitHub auto-disables scheduled workflows after 60 days of repo inactivity, and a mis-set cron simply never fires; in both cases no alert is ever sent, so a retrain/monitor pipeline can silently stop until a stale champion causes an incident.
Fix: an external heartbeat / cron-monitor ping on success.

### R2-16 The `s3_wide` example has no automated test [MLOps · S]

`snowflake_wide` got a guarding pytest (commit 0dd3727) but `s3_wide`, added the next commit, has no test anywhere, so its README's `mbt parse --project-dir examples/s3_wide` is unverified in CI.
Impact: a spec-schema change silently rots the example and a user's first `mbt parse` on it may fail; inconsistent with the sibling example's own precedent.
Fix: a parse-only guard mirroring the Snowflake one.

## P2 - adapters (the warehouse serving leg)

### R2-17 Warehouse scoring is only half-built (issue #1) [MLOps + DS · L]

The Spark data adapter has no `build_scoring_input`/`open_predictions`, so `require_scoring_capability` (`orchestrator.py:386`) hard-fails a Spark team at `mbt score`/`mbt monitor` before any job runs.
Even the "done" Snowflake side returns a `LocalPredictionStore` rooted at local disk (`mbt_snowflake/adapter.py:360-371` -> `predictions.py:48-59`, which cannot target `s3://` or a warehouse table), so predictions and the ground-truth ledger markers land on whatever ephemeral disk the job ran on.
Impact: the production loop never closes for the exact warehouse-native audience the tool targets, and materializing results back into the warehouse - dbt's defining act - is unmet; this is the substantive half of issue #1 that "Snowflake got an implementation" understates.
Fix (L): a warehouse/object-store-native prediction store (the v2 spec is already sketched in ADR-23; it is blocked on the first credentialed `live_snowflake` run).

### R2-18 Regression and native-categorical support stop at the JVM boundary, causing silent cross-adapter parity breaks [DS + MLOps · M each]

`supported_tasks` is `{BINARY_CLASSIFICATION}` for H2O and Spark, and both `_scores` are hardwired to a probability column, so a regression `ModelSpec` on a Spark/H2O target is rejected at parse; separately, Spark's `VectorAssembler` path has no `StringIndexer`, so a string feature that trains fine on xgboost/lightgbm/H2O raises a raw JVM `IllegalArgumentException` on Spark instead of mbt's actionable error.
The tree adapters encode categoricals via the shared `encoding.py`, but H2O/Spark (path access) bypass it, so the "features derived identically -> apples-to-apples champion/challenger" guarantee only holds among the two arrow adapters.
Impact: "same spec, different adapter" - a core selling point - breaks for the whole regression vertical and for any dataset with string features the moment Spark is the challenger.
Fix: `GBTRegressor`/H2O regression score paths (M each) and a StringIndexer stage on Spark with an actionable pre-check.

## P3 - polish and smaller gaps

- **R2-19 `mbt monitor` crashes on an unparseable `scored_at`** [MLOps · S]: `_parse_ts` (`monitor.py:57-58`) does bare `datetime.fromisoformat`; a `ValueError` from one malformed sidecar (e.g. a run written by an external store) escapes `MbtError` handling and poisons the whole node with an unactionable message. Guard-and-skip.
- **R2-20 Window/maturity durations are limited to d/w/h** [DS · S]: `windows.py:19-20` has no months/years, yet `label_time_offset` supports `mo` (`data.py:47`); a "3 month" maturity lag must be approximated as `90d`. Asymmetric vocabulary; add `mo`/`y`.
- **ECE uses equal-width bins** [DS · S]: `metrics.py:88` `linspace` binning is noisy for skewed churn scores; switch to equal-frequency (adaptive) binning.
- **Serial `--fail-fast`/timeout cancellation** [MLOps · S]: `cancel_active_jobs` blocks up to `wait(timeout=5)` per handle (`runners.py:191-199`, `compute.py:107-111`), so 16 in-flight jobs take up to ~80s to reclaim; killed job payloads under `/tmp/mbt-job-*` also never age out. Parallelize terminate; fold payload age-out into `mbt clean`.
- **`mbt evaluate` builds dataset deps sequentially** [MLOps · S]: `orchestrator.py:459-461` bypasses the scheduler, so a multi-dataset re-eval ignores `--threads`/`--fail-fast`, unlike every sibling command.
- **Explainability is global normalized-gain only** [DS · L]: no SHAP, PDP, or local per-prediction attribution; gain importance is cardinality-biased and cannot answer "why did this customer score high."
- **Multiclass / ranking / survival / forecasting absent** [DS · L]: multiclass is architecturally blocked by the single prediction-probability column that is load-bearing across predict -> store -> monitor -> ground-truth (ADR-24); attempting it yields a clean `ConfigError` (good) but the most common non-binary tabular task is unavailable.
- **Optuna engine is thin** [DS · S-M]: hardcoded `TPESampler` + `MedianPruner`, single-objective, sequential (`engine.py:56,62`); no sampler choice, `multivariate=True`, `n_jobs`, or multi-objective/Pareto.
- **No pruning on Spark HPO** [MLOps · L]: `train_with_report` exists only on the tree adapters, so each Optuna trial full-trains a GBT across executors - the most expensive place to skip pruning.
- **H2O `load()` discards column context** [DS · S]: `adapter.py:318` returns empty `features`, so `feature_importance` on a reloaded MOJO returns `{}` and champion cards lose the importance table; write a columns sidecar like Spark does.
- **MLflow alias-mode promotion never archives the outgoing champion** [MLOps · S]: `adapter.py:210-223` leaves the previous champion alias-less rather than archived, so "list archived models" differs between alias and stage backends and rollback is manual re-promotion only.
- **Cross-adapter split membership is not identical** [DS · S docs / M align]: local, Snowflake, and Spark use three different MD5 primitives, so the same key buckets differently per backend and metrics are not comparable across adapters; the Spark docstring's "same md5-threshold formula" claim (`data.py:11`) overstates the parity (only the modulus structure is shared).
- **Spark rejects `--deep-snapshot`** [MLOps · M]: `data.py:124` raises "not supported yet," but CLAUDE.md notes scaffold CI passes `--deep-snapshot` on every compiling step (fresh-checkout mtimes, ADR-11), so a Spark-backed project on the standard scaffold CI fails.
- **The showcase is an oversized, already-drifting surface** [MLOps · S resync / L slim]: 19 compose services plus ~2,000 lines of bespoke glue and ~10 pinned upstream workarounds; `DESIGN.md` names tests/profiles/dashboards that no longer exist (`DESIGN.md:36,165,225,236-239`) and the locally-built runner base is `FROM python:3.11-slim-bookworm` (floating tag, no digest) contradicting its own digest-pinned reproducibility claim. Resync DESIGN.md and pin the runner base now.
- **Monorepo release tax** [MLOps · M]: 11 hand-synced `0.1.0` versions guarded (not bumped) by `test_version_sync.py`, no CHANGELOG anywhere, no release/versioning section in CONTRIBUTING; every release is a manual 11-file edit.
- **No first-class rollback or incident runbook entry** [MLOps · S doc / M tooling]: no `mbt rollback`, no rollback entry in `troubleshooting.md`; the only revert is re-promoting a prior version via `promote.yml`'s `workflow_dispatch`, undocumented as an incident procedure.
- **Leakage scan is univariate and train-split only** [DS · P3]: `checks.py:262-292` screens single-column association on the train split; it cannot see multivariate or target-encoding leakage, or leakage that only appears in test. Document the ceiling so users do not over-trust it.
- **Free-threaded-build safety** [MLOps · P3]: `ExecutionContext.next_index` and `_dataset_handles` are unlocked shared state touched from pool threads; safe under the GIL (Review 1 confirmed), but genuinely racy under a free-threaded `3.13t`/`3.14t` build, which the CI matrix does not yet exercise. Add a lock when free-threaded builds enter the matrix.

## What is genuinely solid (do not touch)

- The compute/subprocess seam: `_SUCCESS`/result-file completeness markers, watchdog SIGTERM -> SIGKILL grace, result-file-over-terminated ordering, and the public `parse_job_line`/`result_path_for` seam remote adapters reuse.
- The scheduler's concurrency reasoning: in-plan-parent counting, `nx.descendants` skip propagation, the threads-bounded outstanding-futures cap that lets `--fail-fast` actually reclaim work.
- Metric parity by construction: every adapter's `evaluate` routes through `evaluate_split` -> `compute_results`, the strongest real parity guarantee in the codebase, and the paired-bootstrap champion gate is genuinely paired, direction-aware, and degenerate-resample-safe.
- Secret hygiene: unrendered configs in the manifest and `taint`/`redact` on every serialization path, including the CLI catch-all.
- The always-on, two-tier, numeric + categorical leakage scan with a deliberately planted leak pinned by a test - excellent DS pedagogy.
- Repo-side CI is well-hardened (concurrency groups that never cancel main, per-job timeouts, 3.11-3.14 matrix, a floors job, gitleaks + CodeQL + dual-resolution pip-audit) and the durable-state GitOps scripts are git-plumbing-only with retry - the standard the scaffold (R2-13) should be brought up to.
- The optional-capability contract (`runtime_checkable` protocols + compliance suite) and ADR-14 import hygiene, both enforced by tests.

## Review 2 - progress log

- 2026-07-21: DONE (R2-7 part 10 - the backtest reports fold-to-fold std, not just the mean) - the cross-validated backtest now reports `mean ± std` per metric, the standard CV output, so an unstable model whose folds disagree is distinguishable from a stable one with the same mean.
  Symptom: parts 1-9 reported only the MEAN across folds. The mean de-luckifies the point estimate, but it hides DISPERSION: a model scoring 0.8 on every fold and one swinging 0.6-1.0 both report 0.8, yet the second is not to be trusted. Reporting only the mean is a genuine incompleteness - every CV tool (sklearn's `cross_val_score`, every ML text) reports mean ± std for exactly this reason.
  Fix: `_walk_forward_backtest` now collects the per-fold metric values and returns `(means, stds)` - the mean plus the population std (`statistics.pstdev`) across folds. The std flows through the same path the mean already travels (`JobResult.backtest_std` -> `NodeResult.backtest_std` -> the model card), and the card renders each backtest cell as `mean ± std`. The `source: backtest` gate still gates the mean (dispersion is a report signal, not a threshold); the std is additive, so a result without one (older payloads) renders the mean bare.
  Verified: a fast-suite job test drives three folds with deliberately disagreeing metrics (0.4, 0.6, 0.8) and asserts the reported std equals `pstdev` (~0.1633) and is non-zero, while identical folds report std 0.0; the docsgen test asserts the `mean ± std` cell and the bare-mean fallback. Falsified by zeroing the std (`0.0 != 0.163299`, the disagreeing-folds test fails). Fast suite green with coverage (1013 passed, 45 skipped, 100.00% - the CI gate); full JVM e2e tier green (60 passed, incl. the Spark and H2O direct-backtest tests, updated to unpack the pair); golden unaffected (the std is a runtime result field, not a manifest field); mypy strict over all 10 packages, ruff, yamllint, pre-commit, and `mkdocs build --strict` all clean.
  Docs: `docs/spec-reference.md` now says the card reports each metric's cross-validated mean and its population std across folds (rendered `mean ± std`), so an unstable model is visible at a glance.
- 2026-07-21: DONE (R2-7 part 9 - temporal nested CV) - nested cross-validation now works on temporal (walk-forward) splits, mbt's DEFAULT, not just random; nested CV is complete for both splits.
  Symptom: part 8 shipped nested CV but scoped it to the RANDOM split, because the implicit validation carve (`_carve_validation`) computed its boundary from the declared FULL train window - wrong for a fold, which is a sub-window. That left nested CV unavailable on the temporal split, which is mbt's default, so most users could not use it.
  Fix: `_carve_validation` gains an optional `time_range` that overrides the declared window with the fold's own `[start, end]`; the main path leaves it None and is byte-unchanged (surgical). The nested backtest, for a temporal outer fold (an expanding walk-forward prefix), passes the prefix's own time span, so the inner tuning's validation is the TEMPORAL TAIL of that prefix - train on the fold's older past, validate on its recent past - and the outer-test fold (in the future of the whole prefix) never informs the selection. The random-only validator restriction is dropped; `nested_cv` now works on either split.
  Verified: a fast-suite job test proves the temporal nesting is correct - the outer walk-forward folds, and within each the inner-tuning validation ends IMMEDIATELY BEFORE the outer-test fold (`max(validation time) == min(outer-test time) - 1`), i.e. the tuning validates on the fold's recent past and never on its future; the spec-validator test now accepts temporal `nested_cv`. ## Executive summary

mbt is an unusually well-engineered v0.1 for its stated scope: the compile/hash/manifest core, adapter contracts, secrets handling, and test layering are genuinely strong.
The biggest problems are not in what exists but in the gap between what the project promises and what it enforces.

The five findings I would fix first:

1. **The shipped reference workflows install the toolchain unpinned** (`pip install mbt-core mbt-xgboost mbt-mlflow`), which contradicts the reproducibility promise the whole tool is built on (P1).
2. **Champion/challenger promotion decisions are single point-estimate deltas with no statistical uncertainty**, so a challenger can be promoted on test-set noise (P1).
3. **The pre-commit ruff rev (`v0.5.0`, June 2024) is two years behind the ruff CI actually runs (`0.15.20`)**, so local hooks and CI enforce different lint/format rules (P1).
4. **Toolchain versions lag latest stable across the board**: Python 3.11 only (3.14 is current), PySpark 3.5 (4.1 is current), GitHub Actions several majors behind, and MLflow registry stages used via a deprecated API (P2, detailed below).
5. **Monitoring, the sixth ml-ops.org principle, is essentially absent**: no OTel, no drift detection, no alerting, no serving-side signal of any kind (P2, partially acknowledged as deferred).

Strengths worth keeping:

- The NFR-04 guard that asserts no ML framework imports on mbt-core's import path is exactly the kind of architectural test most teams never write (`ci.yml:26-38`).
- The three-tier split (lint/type, unit, JVM-provisioned e2e) keeps the fast lane fast (`ci.yml:9-64`).

Gaps:

- P1: all four scaffold workflows install unpinned (`pip install mbt-core mbt-xgboost mbt-mlflow` at `pr_check.yml:28`, `prod_build.yml:25`, `promote.yml:32`, `scheduled_retrain.yml:20`).
  A tool whose README promises "the compiled manifest pins everything" (`README.md:84-88`) ships reference CI where the training environment floats on every run, which invalidates the env digest across runs and directly undermines G2/NFR-01.
  Fix: generate a `requirements.txt` or `uv.lock` in the scaffold and install with hashes.
- P2: no test coverage measurement at all (no `pytest-cov` in any `pyproject.toml`, bare `pytest -q` at `ci.yml:50`); 170+ tests with zero visibility into what they exercise.
- P2: no security scanning of any kind: no `pip-audit`, no CodeQL/bandit, no `gitleaks`, no Dependabot, on a codebase that resolves warehouse credentials (`config/profiles.py`).
- P2: the mkdocs site is never built in CI and never published, and there is no release/PyPI pipeline (acknowledged as deferred in `docs/v0.1-status.md:26`), so docs rot silently and the 10 "publishable" packages have no publish path.
- P2: no failure alerting in any workflow; a failed Monday 05:00 scheduled retrain (`scheduled_retrain.yml:7`) fails silently, which violates the Continuous Training principle's operational side.
- P2: `prod_build.yml:34-45` writes the "published" manifest into the ephemeral workspace and only uploads a per-run artifact, so out of the box there is no durable prod state baseline and the `state:modified` economy loop (G3) is a no-op until someone hand-wires S3.
- P3: no uv cache in CI (`setup-uv@v5` without `enable-cache`), so every job re-resolves the workspace.

### 2.2 Reproducibility and versioning (ml-ops.org: Reproducibility, Versioning)

Strengths worth keeping:

- The two-hash identity model (config hash + transitive input hash, profiles excluded) is sound and golden-tested (`compile/hashing.py:31-44`, `tests/test_golden_manifest.py`, ADR-4/ADR-5).
- Snowflake snapshot pinning with hard failure on drift, and deterministic push-down sampling, are the right design (`mbt_snowflake/adapter.py:151-164`, `mbt_snowflake/sql.py:63-77`).

Gaps:

- P2: `env_digest` hashes only Python micro, `mbt-*` versions, and adapter `fingerprint_packages` (`compile/hashing.py:47-60`); a numpy or scipy bump that changes XGBoost numerics is invisible to it.
  Include a hash of the resolved environment (e.g., `uv.lock` hash or `pip freeze` digest) in the manifest.
- P2: `mbt build --manifest` never verifies the env digest at rebuild time; it is only a `state diff` signal (`state/diff.py:30,118`), so "reproduce this manifest" silently proceeds in a mismatched environment.
- P2: `mbt deps` installs adapters via `pip install` against loose PEP 440 specifiers from `packages.yml` with no lock or hash verification (`deps.py:44-59`).
- P3: the default local snapshot is mtime-based, which ADR-11 itself admits "lies" in CI and fresh checkouts; `--deep-snapshot` (content hashing) should be the default, or at least the default in CI.

### 2.3 Registry, promotion, deployment (ml-ops.org: Deployment, CD)

Strengths worth keeping:

- Promotion refuses versions whose gates were not recorded as passed, and `--force` is auditable (`promote.py:84-108`).
- Champion re-evaluation in-job on the identical pinned split (ADR-9) and the missing-vs-unloadable champion distinction (ADR-10) are principled.

Gaps:

- P2: there is no serving, batch scoring, or inference surface at all; `mbt score` is v1 roadmap (`docs/roadmap.md:24`), and exposures are descriptive metadata only (`artifacts/manifest.py:65-73`).
  ml-ops.org's deployment principle expects the model to reach a prediction service; today the pipeline ends at the registry, which is a legitimate v0.1 scope cut but means the tool cannot yet close the loop it draws in its own GitOps diagram.
- P3: no first-class rollback; promotion to Production auto-archives the incumbent (`mbt_mlflow/adapter.py:216`), so recovery from a bad promotion is a manual re-promote, and MTTR (an ml-ops.org delivery metric) has no tooling.

### 2.4 Monitoring and observability (ml-ops.org: Monitoring, Continuous Monitoring)

- Strength: typed Pydantic events with console and JSON-lines sinks, redaction on every write, machine-readable `run_results.json` (`events/models.py`, `events/sinks.py:31-58`).
- P2: OTel is documented as deferred (`docs/v0.1-status.md:22,41`) and nothing exports to standard observability backends.
- P2: no statistical drift detection exists anywhere; all quality checks run at build time against training data (`quality/checks.py:210-216`), and `docs/quickstart.md:112` mislabels champion re-evaluation as a "drift check", which conflates data versioning with distribution monitoring.
- P2: no alerting integration (no slack/webhook/pagerduty anywhere in `_scaffold` or `.github`).

### 2.5 Secrets

- Strength: env_var-only ingress, taint-and-redact on all sinks, and the manifest stores target config unrendered so secrets never reach the primary artifact (`config/profiles.py:90-116`, `secrets.py:18-52`, `artifacts/manifest.py:47-49,143`).
  This is better than most production ML platforms.
- P3: `redact()` is exact-substring replacement of tainted values only (`secrets.py:45-52`); secrets read directly from `os.environ` in hooks/adapters, or transformed (base64, URL-encoded), escape redaction.

### 2.6 Storage and artifact lifecycle

- P2: the artifact store is `file://` only (`storage.py:16-20`); trained models cannot land in object storage, which blocks any multi-runner or production topology.
- P2: there is no retention, GC, or pruning of `target/` or the artifact store; every run writes a new uuid prefix forever (`storage.py:23,29-39`), and the repo's own `target/fake_tracking/` full of leftover test JSON illustrates the unbounded growth.
- P3: tests write into the repo-root `./target` instead of a tmp dir (`tests/test_perf_budgets.py:36`), polluting the working tree.

### 2.7 Testing infrastructure (ml-ops.org: Testing)

Strengths worth keeping:

- The per-adapter compliance suite (determinism tiers, import hygiene, export/load round-trip, "actually learns") is a reusable conformance asset (`mbt_adapter_base/compliance/suite.py:161-256`).
- Golden manifests, perf budgets, property tests, and spec-only adapter swap are a layered strategy most tools this age lack.

Gaps:

- P2: `docs/v0.1-status.md:24` claims "mutation" testing under NFR-08, but no mutation tool (`mutmut`, `cosmic-ray`) exists in any dependency set; the only "mutation" is a test-name string in `test_compile.py`.
  Either add mutation testing or correct the status doc; a status document that overstates rigor is worse than the gap itself.
- P3: no flaky-test mitigation (no `pytest-rerunfailures`, no `pytest-xdist`, no `pytest-randomly`) even though the JVM e2e tier (H2O/Spark) is flake-prone by nature.
- P3: perf budgets are bare wall-clock asserts on shared CI runners with no warmup or tolerance (`tests/test_perf_budgets.py:87,98,117`), which will flake under noisy neighbors.

### 2.8 Documentation and operability

- Strength: 17 ADRs, a spec reference, quickstart, gitops and adapter-authoring guides; unusually complete for v0.1.
- P2: no troubleshooting guide or runbook exists for the failure modes the code deliberately produces (snapshot mismatch, unloadable champion, gate-edit retrain signals); operators have design docs but no playbook.
- P3: doc drift: `docs/v0.1-status.md:25` says "15 ADRs" while 17 exist; small, but this is the document that markets the project's rigor.

## 3. Data science findings

### 3.1 Task coverage

- P2: only binary classification works end to end; the task registry hardcodes a single entry (`config/tasks/__init__.py:11-13`) and every adapter pins `supported_tasks = {BINARY_CLASSIFICATION}` (`mbt_xgboost/adapter.py:67`, `mbt_lightgbm/adapter.py:61`).
  The extension seam (`register_task_schema`) is clean, so regression should be the next vertical; a "dbt for ML" that cannot fit a regression is a hard sell to most DS teams.
- P2: the metric layer is binary-only (`mbt_adapter_base/metrics.py:21-32,140-167`); no RMSE/MAE/R2 or multiclass path exists.

### 3.2 Splitting and validation protocol

Strengths worth keeping:

- Temporal split as the default, resolved as disjoint SQL time windows against a single anchor, is the right call for the churn-style use case (`adapters/local/data.py:228-248`, ADR-12).
- Random splits require an explicit seed, and hash-based ranking over `sample_key` gives implicit entity-grouped splits when `sample_key` is the entity id (`specs.py:93-96`, `data.py:195-208`).

Gaps:

- P2: there is no explicit grouped-split control and no warning when it is absent; without `sample_key`, the row digest falls back to all columns (`data.py:200-203`), so the same customer can straddle train and test with no signal to the user.
- P2: `strategy: random` is allowed on datasets with a time column and nothing detects or warns about the temporal leakage this invites (`specs.py:72,92-109`); the framework should at minimum warn when a random split coexists with a time column.
- P2: no cross-validation exists anywhere; tuning selects on a single validation carve (see 3.5) and H2O's `nfolds` defaults to 0 (`mbt_h2o/params.py:28`).

### 3.3 Metrics

- Strength: the binary set is genuinely good: `roc_auc, pr_auc, logloss, brier, ece, recall_at_precision, precision_at_recall` with parameterized sugar, computed identically across adapters on the held-out test split (`metrics.py:21-53`, `execute/job.py:456-460`).
- P2: no lift/gain/decile or top-k precision as first-class metrics; the churn demo hand-rolls `lift_at_decile` as a hook (`examples/churn_demo/models/churn_classifier.py:4-14`), yet lift tables are the lingua franca of churn/marketing DS.
- P2: slice metrics silently drop degenerate slices (`metrics.py:160-161`) and slicing a continuous column explodes into one slice per unique value with no binning.
- P3: `accuracy` uses a fixed 0.5 threshold with no operating-point selection (`metrics.py:129`).

### 3.4 Evaluation gates

- Strength: the gate engine is pure and direction-aware, tolerance widening applies only in the model's favor on absolute gates, and missing-champion bootstrap passes loudly (`quality/gates.py:35-116`, ADR-10).
- P1: champion comparison is a bare point-estimate: `passed = delta >= gate.min_delta` (`gates.py:92-97`).
  There is no bootstrap CI, no paired test, and no accounting for test-set size, so with the small test windows typical of temporal splits a challenger can be promoted on noise; `min_delta` is the only, blunt, mitigation.
  A paired bootstrap over per-example scores is cheap (both models' predictions on the identical pinned split are already in hand thanks to ADR-9) and would make the promotion decision statistically defensible.
- P2: slice gates are contradictory: `gates.py:16-25` fully evaluates them, but `specs.py:204` and `docs/v0.1-status.md:31` call them report-only/deferred; either the docs understate a shipped capability or untested behavior is shipping.

### 3.5 Hyperparameter tuning

- Strength: seeded TPE with clean search-space validation, tuning seed derived separately from the training seed, and ADR-8 ("tuning never sees test") verified in code: trials score on validation only, and an implicit carve is reabsorbed into the final fit while an explicit one stays held out (`mbt_optuna/engine.py:16-59`, `execute/job.py:387-423`).
- P2: best-trial selection is max-over-n-trials on one small validation set (often an implicit 20% carve), a classic optimistic-bias setup with no CV, repeated folds, or re-validation of the winner (`engine.py:60-63`, `job.py:295-322`).
- P3: no Optuna pruner and no `trial.report()` integration, so every trial trains to completion (`engine.py:51-59`), which is wasteful at scale.

### 3.6 Leakage protections

- Strength: the split time column is always stripped from features on every materialization path (`execute/handles.py:30-50`, `job.py:160`), and window-expression hashing means anchor drift cannot silently shift train into test (ADR-12).
- P2: beyond that, leakage prevention is user discipline: `label_leakage_scan` is opt-in, numeric-only, and fires only at `|corr| >= 0.95` (`quality/checks.py:148-185`); the churn demo does not even enable it, and sibling-label exclusion is manual (`churn_classifier.yml:14`).
  A framework whose README markets "explicit leakage guards" should enable the scan by default and lower the bar.
- P2: `no_future_columns` only catches values later than the newest window end (`checks.py:110-145`), i.e. absolute-future timestamps, not train/test overlap.
- P3: the demo's `test_no_leakage.py` tests label binarity and an activity filter, not leakage (`examples/churn_demo/tests/test_no_leakage.py:7-22`); the filename writes a check the code does not cash.

### 3.7 Feature handling and explainability

- P2: no native categorical support: both tree adapters densify to float and hard-error on any non-numeric column (`mbt_xgboost/adapter.py:133-166`, `mbt_lightgbm/adapter.py:122-146`), even though both frameworks support categoricals natively (`enable_categorical`, `categorical_feature`).
  The demo consequently throws away `plan_type`, its only categorical and a plausibly predictive feature (`churn_classifier.yml:14`).
- P2: no feature importance, SHAP, or any explainability output anywhere; model cards render hyperparameters and metrics only.
  For a tool that positions model specs as reviewable governance artifacts, a per-model importance table in `mbt docs generate` is table stakes.
- P2: no fairness tooling: slices exist, but there is no disparity metric or fairness gate, which ml-ops.org lists under model-development testing.

### 3.8 Class imbalance

- Strength: `{{ auto }}` `scale_pos_weight` computed from the observed class balance in both tree adapters, with a parse-time warning path for extreme imbalance (`mbt_xgboost/adapter.py:105-123`, `config/tasks/binary.py:75-86`).
- P2: no threshold tuning or calibration step exists; probability reweighting is the only lever, and the calibration metrics that do exist (brier, ece) are never exercised by the demo, despite churn probabilities being what interventions consume.

### 3.9 The churn demo as a DS exemplar

- Strength: the scaffolding is methodologically correct: temporal split, id and sibling-label exclusion, PR-AUC primary, champion/challenger pair, slice reporting.
- P2: the gate is vacuous: `pr_auc_floor: 0.05` (`examples/churn_demo/mbt_project.yml:5`) against a ~20% positive rate whose random baseline PR-AUC is roughly 0.20, so any non-degenerate model passes and the demo's "quality gate" never actually gates.
  The first thing a prospective user copies from the example is a threshold that teaches the wrong lesson; set the floor above the base rate.
- P3: 2,400 synthetic rows with a logistic label generated from the same three features the model uses (`scripts/generate_data.py:16,38`) cannot surface collinearity, drift, or leakage; a slightly richer generator (irrelevant features, a deliberately leaky column for the scan to catch, more rows) would make the demo a teaching asset.

## 5. What is genuinely good (keep it)

- The two-hash reproducibility model with golden-manifest byte-determinism testing.
- The NFR-04 CI guard keeping ML frameworks off mbt-core's import path, and the adapter compliance suite as a conformance contract.
- ADR-8/9/10 discipline: tuning never sees test, champions re-evaluated on the identical pinned split, missing-vs-unloadable champion distinction.
- Secrets: env_var-only ingress, taint-based redaction on every sink, unrendered target config in the manifest.
- Warehouse-native snapshot pinning with hard drift failures and deterministic push-down sampling.
- Seventeen ADRs that record why, not just what; most teams cannot answer "why is this lazy import here" two years later, and this repo can.
