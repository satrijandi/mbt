# FEEDBACK v2: a fresh DS / DE / MLOps review of mbt

Review date: 2026-07-21, against `main` (`a4c2230`).
Perspective: a senior data scientist, a senior data engineer, and a senior MLOps engineer, each re-reading the tree from their own workflow.
Method: six parallel deep-verification passes (DS methodology, MLOps resilience, the data-engineering layer, core-engine correctness, adapter parity, and DX/docs/testing), each cross-checked against the now-closed Review 2 progress log so nothing already fixed is re-litigated as new.
Every finding carries file evidence, the perspective it hurts, and an impact x effort score (S = hours, M = days, L = weeks).
The tree is green at review time: the fast suite is `1013 passed, 45 skipped, 100.00% coverage`, `mkdocs build --strict` is clean, and the full first-run loop (`init` -> `build` -> `promote` -> `score` -> `monitor` -> `docs`) runs to exit 0.
So this is a review of gaps and risk, not of a broken tree.

## The honest top line

Two things are true at once, and holding both is the point of this review.

First, the 2026-07-21 sweep that closed almost all of Review 2 is **real, not cosmetic**.
The additions are genuine implementations, not stubs: calibration fits and persists and round-trips on all four training adapters, the walk-forward / k-fold / nested cross-validation is correct where it runs, JVM regression really dispatches `GBTRegressor`, the Optuna sampler choice is reachable end to end.
Test quality is genuinely high: zero `MagicMock` across 123 test files, real xgboost/lightgbm and real fake-adapter implementations, explicit anti-tautology guards, and honest coverage qualification.
That is rare, and it should be said plainly before the criticism.

Second, the sweep's **method** left one specific, repeating class of gap.
The fixes are vector-specific, not class-specific, and the new features were built in isolation and never tested in combination.
Six confirmed bugs (four reproduced end to end) sit exactly in those seams, and several of them **silently defeat the very Review 2 items that are marked DONE**.
This is the throughline of the whole review, so it gets its own section next.

The remaining problems have moved to five places:

1. One organizational action gates the entire product (the tag + PyPI publish).
2. Newly-added features that do not compose (the confirmed bugs).
3. The data-engineering layer's depth (the perspective both prior reviews under-weighted, and the one you asked to foreground).
4. Capability-summary documentation that the feature work did not update in lockstep.
5. The strategic fact that mbt has only ever been validated against itself.

## The throughline: fixes closed the named vector, not the class

A review-driven loop optimizes for "close the finding," and a finding names exactly one vector.
So the fix lands on that vector and its siblings stay open.
This is not hypothetical; it is the shape of almost every confirmed bug below.

| Review 2 item, marked DONE | What the fix did | The sibling vector it left open |
|---|---|---|
| R2-3 atomic control-file writes | `os.replace` (crash-visible-safe) | no `fsync`, so a power-loss still truncates the manifest (F13) |
| R2-10 pinned-manifest scoring | removed `_verify_snapshot` from `build_scoring_input` | the materialization cache in front of it serves a stale batch (F4) |
| R2-11 evaluated-exactly-once ledger | made marker *existence* atomic (`O_EXCL`) | marker *content* is a separate write, so a crash leaves a 0-byte poison and reintroduces R2-19 (F3) |
| R2-2 retry on external I/O | S3 (jittered) + mlflow writes | mlflow reads unprotected, mlflow retry has no jitter, Snowflake data plane has nothing (F9, F10, F14) |
| R2-8 calibration on all adapters | wired the calibrator on 4 adapters | crashes when combined with the backtest (F5); crashes on a standalone Spark install (F7) |
| R2-7 embargo + backtest | both shipped the same day | they do not compose: the backtest ignores the embargo and leaks (F6) |
| R2-15 dead-man's-switch heartbeat | pings on `success()` | a legitimate exit-2 quality breach trips the switch and false-pages (F11) |

The antidote is structural, and it appears twice in the recommendations: a compliance / integration test matrix that **crosses** features rather than testing each once, and dogfooding, which exercises the combinations no written finding will ever name.

## The three things I would fix before anything else

1. **Cut `v0.1.0` and let the product exist (F1).**
Zero git tags and nothing on PyPI means the flagship PR -> CI -> registry loop cannot run for a single real user, and the whole reproducibility promise is undelivered at the user edge.
This is one human action, and it is the highest impact-to-effort ratio in the repo.

2. **Fix the six confirmed bugs (F2 through F7).**
All are S or M, four are reproduced, and three of them silently defeat a Review 2 item that currently reads as closed.
They are exactly the combinations a first real user hits: a duplicated feature row, a crashed monitor, a pinned-manifest scorer, a calibrated model with an honest backtest.

3. **Dogfood one real model, end to end, with one real data scientist (strategic).**
mbt has never met messy data or a user who did not write it.
This will surface more than a seventh self-review, and it is the only thing that reliably exposes the feature-combination class above.

## P0 - the organizational blocker

### F1 The product does not exist yet at the user edge [MLOps / DX - High - S (human action)]

`git tag -l` is empty and nothing is on PyPI, yet `cli/scaffold.py:53` stamps `mbt.__version__` (`0.1.0`) into every `mbt init` project, which pins `mbt-core @ git+https://github.com/satrijandi/mbt@v0.1.0` in `requirements.txt`.
A fresh project's first CI step is `pip install -r requirements.txt` (`_scaffold/.github/workflows/pr_check.yml`), so it fails immediately on a tag that does not exist.
The publish-gate half of R2-1 is correctly done (`release.yml` now gates on CI via `workflow_call` and uses `skip-existing`), so the moment the tag is cut, the loop works.
Two actionable residuals until then: the trap is invisible (the scaffold README presents the workflows as working, and `troubleshooting.md` has no entry for the git-ref install failure), and, per F7, the wheel smoke test does not prove each adapter installs standalone.
Fix: cut the tag and create the PyPI projects (organizational); until then, add a scaffold-README note plus a troubleshooting entry, or point the pins at `@main` with a comment.

## P1 - confirmed bugs (correctness; fix before wider adoption)

### F2 Multi-table joins silently fan out, there is no uniqueness contract, and ADR-22 claims the opposite [DE - High - M]

A feature or label table that is not unique on its join key multiplies spine rows through a plain equi-join (`local/data.py:273-296`, `snowflake/sql.py:109-111`, `spark/data.py:247`).
All copies of an entity share one split (split is `hash(sample_key)`), so this is not leakage; it is worse for a data engineer, because the fanned-out entity is silently over-weighted in both training and the reported test metric, and `roc_auc`/`pr_auc` are then computed on a row-duplicated test set.
There is no way to declare the contract away: `BUILTIN_CHECK_NAMES` is exactly `{schema, not_null, no_future_columns, label_leakage_scan, class_balance_report}` (`quality/check_names.py:15-23`), so dbt's `unique` and `relationships`, the two checks that would catch this, are both absent.
ADR-22:55-56 asserts "the label join never invents rows (an inner join can only shrink the spine)", which is factually false for a non-unique right side and was empirically falsified (a 3-row spine produced 4 rows).
Fix: add `unique` and `relationships` dataset checks usable on sources pre-join, an optional 1:1 join-cardinality assertion on `inputs`, and correct the ADR-22 claim.

### F3 The ground-truth ledger marker is content-non-atomic, permanently poisoning a run [MLOps - High - S] (reproduced; defeats R2-11, reintroduces R2-19)

`LocalPredictionStore.write_marker` (`mbt_adapter_base/predictions.py:97-105`) creates the marker with `O_CREAT|O_EXCL` (existence is atomic) and then writes its JSON body in a **separate** step, so a crash, an OOM kill, or a concurrent reader in that window sees a zero-byte file.
`read_marker` (`predictions.py:76-82`) does a bare `json.loads(path.read_text())` with no empty guard.
Reproduced end to end: the empty marker makes `write_marker` return `False` forever (the run is treated as already-evaluated, so its realized-metric evaluation never happens and the ground truth is permanently lost), and the `JSONDecodeError` (a `ValueError`) escapes `run_with_lifecycle`'s `except MbtError` at `monitor.py:203`, poisoning the node with the unactionable message R2-19 was closed to prevent; `mbt predictions ls` hits the CLI catch-all and prints "Internal error ... a bug in mbt."
The R2-11 fix made the dedup guarantee real but stopped at existence, not content.
Fix: write the body to a same-dir temp file, `fsync`, `os.link` it into place (create-if-absent plus full content atomically), unlink the temp; and have `read_marker` treat an empty or undecodable file as absent.

### F4 `mbt score --manifest` serves a stale cached batch [MLOps - High - S] (reproduced; defeats R2-10)

R2-10 removed `_verify_snapshot` from `build_scoring_input` so a pinned manifest scores live data, but the `ScoringRunner._materialize_input` cache sits in front of it and short-circuits it.
Under `--manifest`, `materialization_key` (`runners.py:241-256` = `input_hash` + resolved windows + `sample_fraction`) is fully pinned and invariant to the live data, so the key never changes, the `_SUCCESS` probe hits, `from_locator` validates against the pinned `snapshot_id` (which always matches), and `build_scoring_input` is never called.
Reproduced on churn_demo: a first `mbt score --manifest` writes an empty batch; after adding 741 rows inside the pinned window, the same command logs `cache hit` and reports `rows_scored=0`, while a fresh-compile `mbt score` materializes all 741.
`scoring_run_key` is also pinned under `--manifest`, so the stale run overwrites in place and `mbt monitor` then evaluates realized metrics on stale predictions.
The R2-10 test missed it by calling `build_scoring_input` directly, bypassing the runner cache.
Fix: scoring inputs are expected-mutable, so `ScoringRunner._materialize_input` must not reuse a `_SUCCESS`-marked scoring-input materialization; always call `build_scoring_input` (it already wipes and rebuilds one cheap batch). Datasets are unaffected.

### F5 Calibration plus a backtest hard-crashes the training job [DS - High - S to XOR, M to do right] (reproduced)

Two flagship 2026-07-21 features cannot be used together, which is the natural combination for a data scientist who wants both calibrated probabilities and an honest temporal estimate.
`_walk_forward_backtest` builds every fold as `InMemoryDatasetHandle({"train", "test"})` with no `validation` split (`execute/job.py:713-720`), then calls `adapter.train(fold_spec, ...)` with `fold_spec` still carrying `calibration`; every adapter's `_fit_calibrator` then raises `ValueError("calibration needs a 'validation' split")` (e.g. `mbt_xgboost/adapter.py:276-280`).
No `model_validator` makes `calibration` and `backtest_folds` mutually exclusive, so the job returns `status="error"` and nothing registers.
The error is doubly confusing because it tells the user to declare a `split.validation` they already have on the main model.
Fix: sub-carve each fold's train into train+validation (reuse `_carve_validation` on the fold) so the fold model calibrates the way the real model does; a spec-level XOR is only an acceptable stopgap, because otherwise the backtest would compare uncalibrated fold models against a calibrated production model.

### F6 The walk-forward backtest ignores `split.embargo`, so every fold boundary leaks [DS - Med-High - M]

The embargo (R2-7 parts 4-5) exists to stop label-horizon leakage at a split boundary, but it is applied only in `compile/compiler.py:272-281`, which pulls back the resolved train-window end relative to the test split.
`_backtest_folds` reads that already-materialized train window and cuts contiguous folds with `ordered.slice(...)` (`execute/job.py:658-669`), with no embargo gap between a fold's train prefix and its test fold, and `grep -rn embargo packages/mbt-core/src/mbt/execute/` is empty.
So for a population-spine dataset with a `label.time_offset` (the exact case the embargo was built for), training rows at each fold tail have labels observed inside the next fold's evaluation window, and a `source: backtest` gate can promote on an optimistically-biased mean.
Fix: thread `spec.split.embargo` into `_backtest_folds` and exclude rows within `[boundary - embargo, boundary)` from each training prefix, calendar-aware via the existing `subtract_duration`.

### F7 Spark advertises calibration but its dependency closure is incomplete, so it crashes on a standalone install [MLOps / DX - High - S] (verified)

`mbt-spark` declares bare `mbt-adapter-base>=0.1.0,<0.2` (`pyproject.toml:27`), while `mbt-xgboost` and `mbt-h2o` declare `mbt-adapter-base[metrics]`, which is the extra that carries `numpy` and `scikit-learn`.
`Calibrator.fit` imports `sklearn.isotonic`/`sklearn.linear_model` (`calibration.py:43,53`), and Spark's own `_scores` uses `import numpy` and `.toPandas()` (`training.py:261,276`), none of which are in Spark's declared closure.
So a clean `pip install mbt-core mbt-spark` plus `calibration: isotonic` raises `ModuleNotFoundError: sklearn`, and the scoring path needs pandas that is also undeclared; CI never sees this because the uv workspace already pulled those in via the other adapters.
This is a concrete instance of F1's theme: the monorepo masks standalone-install breakage.
Fix: change Spark's dependency to `mbt-adapter-base[metrics]` and add `pandas`; more broadly, make the wheel smoke test install each adapter into its own clean venv.

## P1 - resilience regressions the sweep left open

### F8 The mlflow `transition` retry drops the archived champion under a lock [MLOps - Med-High - S-M] (found independently by two passes)

`transition` is decorated `@_retryable` and reruns the whole method on `database is locked` (`mbt_mlflow/adapter.py:44-54,255`), but it captures the outgoing champion by reading the production alias (line 271) before repointing that alias to the new version (line 275).
If any write after 275 hits the lock, the retry re-reads the alias, now finds the new version, sets `outgoing == version.version`, and the archive guard at 285 goes false, so the true previous champion is never archived and is left alias-less.
This reintroduces exactly the P3 archive-on-promote bug the 2026-07-20 fix closed, under the precise concurrent-writer scenario the retry exists for, and `test_promoting_a_new_champion_archives_the_outgoing_one` never injects a mid-transition lock.
Fix: capture `outgoing` once outside the retried unit, or retry only the individual idempotent client calls.

### F9 `get_champion` swallows every mlflow exception as "no champion", silently disabling the challenger gate [MLOps - Med - S] (found independently by two passes)

`get_champion`/`get_version` do `except MlflowException: return None` (`adapter.py:233-234,238-239,249-252`), conflating "no such champion" with "backend locked / unavailable / 500", and these reads are not retried.
The consumer treats `None` as "no champion" and promotes the challenger as the first champion with no gate comparison (`runners.py:454`), which is asymmetric with ADR-10 one line later (a champion that exists but cannot load is a hard error).
So a transient lock during champion resolution either silently skips the challenger gate on a build or hard-fails a scheduled `mbt score` with "no champion to score with", a false negative dressed as clean state.
Fix: narrow the except to `RESOURCE_DOES_NOT_EXIST` / empty-search and let other exceptions propagate or retry.

### F10 The mlflow lock-retry has no jitter [MLOps - Med - S]

`_with_retry` sleeps `base_delay * 2**attempt` with no randomization (`adapter.py:44-54`), yet it exists specifically for two parallel jobs hitting `database is locked` at the same instant, which is the textbook thundering-herd case that deterministic backoff re-collides on every attempt.
The S3 seam explicitly relies on botocore `standard` mode's exponential-backoff-plus-jitter (`storage.py:16-26`), so the two retriers hold different standards.
Fix: full jitter, `time.sleep(random.uniform(0, base_delay * 2**attempt))`.

### F11 The scaffold heartbeat trips the dead-man's-switch on a legitimate quality breach [MLOps - Med - S]

In `scheduled_monitor.yml` and `scheduled_score.yml` the heartbeat pings `if: success()`, but `mbt monitor`/`mbt score` exit 2 on a realized-metric or shift breach, which fails the GitHub step, skips the heartbeat, and makes the external cron-monitor fire a false "pipeline is DOWN" page when its grace window lapses.
So every real breach double-pages (the quality webhook plus a false liveness alarm) exactly during an incident, which erodes trust in the liveness channel.
Fix: ping the heartbeat whenever the job reached a decision (exit 0 or 2), and reserve the switch for exit 1 or a no-show.

### F12 `mbt rollback` reports success without verifying the target can serve [MLOps - Low-Med - S]

`rollback_model` re-promotes purely on the recorded `mbt.gates_passed` tag (`promote.py:137-180`) and never checks that the target version still has a loadable artifact.
Because `mbt clean` keeps only current champions plus the latest run (`gc.py:37-50`), a rolled-back-to old version's artifact may already be aged out, so the alias moves, "rolled back to v3" prints at exit 0, and the next `mbt score` dies with "champion has no loadable artifact".
An incident-response command should confirm the destination is serviceable before declaring victory.
Fix: assert the resolved version has an artifact (ideally a store `exists`/`head` probe) before the transition.

### F13 Atomic writes are crash-visible-safe but not crash-durable [MLOps - Low-Med - S] (found independently by two passes)

`atomic_write_text` uses a same-dir temp plus `os.replace` (`artifacts/atomic.py:21-32`), which fully covers R2-3's stated threat model (killed process, racing reader), but it never `fsync`s the temp fd before the replace nor the parent dir after.
So a power loss or kernel panic can persist the rename while the data blocks do not, leaving `manifest.json` present-but-zero-length, which reintroduces the "invalid JSON in manifest bricks every subsequent `--state`/`--manifest`/`docs`" symptom under a harder fault.
Both control-file sinks inherit this (`manifest.py:170`, `run_results.py:134`).
Fix: `flush` then `os.fsync(fileno())` before `os.replace`, then fsync the directory fd.

### F14 The Snowflake data plane has zero mbt-level retry [MLOps / DE - Med - M]

R2-2 protected the S3 store and the mlflow writes, but `cursor.execute(sql)` in the Snowflake adapter (`mbt_snowflake/adapter.py:129,249`) fails hard on a transient warehouse blip, and this is the target audience's training and scoring path, not a rare local case.
The DuckDB read/COPY path (`local/data.py:352,390,432`) is the explicitly-deferred remainder of R2-2; the Snowflake plane is the higher-value one that was not named.
Fix: a small generic retry-with-jitter helper plus a per-seam transient-error predicate, applied to the warehouse data plane.

## P2 - data-science methodology

### F15 The n-aware KS "significance" bar does not deliver its nominal level, and is not a KS test at all on categoricals [DS - Med - M] (measured)

`_fail_bar` applies the Kolmogorov two-sample critical value to any `method: ks` stat, numeric or categorical (`quality/monitors.py:34-40`), but `_categorical_ks` returns the max per-category proportion difference (`mbt_adapter_base/monitoring.py:255-266`), a total-variation measure on nominal data that does not follow the Kolmogorov null, and `_numeric_ks` evaluates the sup-gap only at the 101 stored baseline quantiles, which is downward-biased.
Measured under H0 with no true shift at nominal alpha 0.05: empirical false-positive rate 0.032 numeric (about 1.6x conservative) and 0.007 categorical (about 7x conservative), so a categorical shift monitor set to `significance: 0.05` is about 7x less sensitive than advertised and silently misses drift.
Fix: restrict `significance` to numeric KS, evaluate the sup over the merged baseline-quantile plus current-sample points, and use a chi-square / G-test critical value for categorical shift (or reject `significance` on categorical features as a stopgap).

### F16 The disparity (fairness) gate math is invalid for `r2` with no guard [DS - Low-Med - S]

`evaluate_gates` computes `ratio = lo/hi` and assumes non-negativity (`quality/gates.py:83`), and the docstring itself admits this holds "for every builtin except r2", but nothing blocks `across` on `r2`.
Now that regression is a shipped vertical and `r2` is a natural disparity metric, two negative-r2 slices (say -0.9 and -0.1) yield ratio 9.0 and pass a wildly disparate model, while a mixed-sign pair yields a negative ratio.
Fix: reject `across` on `r2` in the validator, or use a gap (max minus min) rather than a ratio for signed metrics.

### F17 Post-hoc calibration is fit on the same split used for model selection [DS - Low-Med - M]

The xgboost adapter uses `data.read("validation")` for early-stopping `evals` and `best_iteration` selection (`adapter.py:210-215`) and then fits the calibrator on that same split (`adapter.py:281-284`); with tuning, the Optuna objective is also computed on `validation` (`job.py:600-601`).
So the reported `ece`/`brier` gain is mildly optimistic and the deployed calibrator slightly overfits, which is the exact reason `CalibratedClassifierCV` holds the calibration set out of model fitting.
This only bites when `early_stopping_rounds` or tuning is combined with calibration.
Fix: carve a dedicated calibration slice, or use cross-validated calibration on the train split. (Related nit: the sigmoid path fits an essentially-unregularized `LogisticRegression(C=1e10)` on raw 0/1 labels, `calibration.py:53-57`, omitting Platt's target smoothing, which overfits the small held-out sets sigmoid is documented to be robust for.)

### F18 The flagship demo still ships miscalibrated by construction and never uses the lever built to fix it [DS - Low - S]

R2-8 was motivated by "the demo sets `scale_pos_weight: auto` while measuring `brier`/`ece`, miscalibrated by construction", and that is still literally true: `churn_classifier.yml:20` sets `scale_pos_weight: "{{ auto }}"`, line 27 measures `brier, ece`, the comment on line 24 says calibration is first-class, and there is no `calibration:` field.
The one example a data scientist copies to learn calibration does not use it.
Fix: add `calibration: isotonic` to `churn_classifier` and let the e2e assert the ece drop, turning the demo into the intended before/after teaching case.

## P2 - data engineering (the under-served perspective)

### F19 Cross-adapter split membership differs, and local split membership drifts as data grows [DE - Med - M]

The three data adapters share the modulus (`SAMPLE_MODULUS = 1_000_000`) but hash different slices of the md5 digest: local `md5_number(...)` is the full 128-bit digest (`local/data.py:311`), Snowflake `MD5_NUMBER_LOWER64` is the low 64 bits (`snowflake/sql.py:71`), Spark `conv(substring(md5,1,15),16,10)` is the top 60 bits (`spark/data.py:80`), so the same key lands in a different bucket per backend.
This is bounded to random splits (temporal, mbt's default, is window-based and unaffected) and is now documented honestly, but it still breaks the dev-local to prod-warehouse workflow that is a data engineer's default, because a model validated on DuckDB does not get the same train/test partition on Snowflake or Spark and the metrics are not on the same rows.
A net-new sub-point: local's random split uses `percent_rank() OVER (ORDER BY hash)` (`local/data.py:376`), which is relative to the whole dataset, so a near-boundary row flips train/test between retrains as data grows, whereas the warehouses' pure-function hash buckets are stable, the opposite of what a data engineer would assume.
Fix: standardize one digest-extraction scheme and cast policy across all three adapters, and either make local use stable bucket ranges too or document that random-split membership is backend- and size-dependent.

### F20 Warehouse predictions still land on local disk, and `predictions_root` defaults to the project directory [DE / MLOps - High to close - L; the default is S]

For the warehouse-native audience the tool targets, `open_predictions` returns a `LocalPredictionStore` rooted at `predictions_root` for both Snowflake and Spark (`mbt_snowflake/adapter.py:374`, `spark/data.py:433-444`), so predictions and the ground-truth ledger land on whatever ephemeral job disk ran, not back in the warehouse or lake.
Materializing results back into the warehouse is dbt's defining act, and it remains the open half of issue #1 (ADR-23 v2, gated on the first credentialed `live_snowflake` run).
Separately, `predictions_root` defaults to `"."`, so a nightly warehouse scoring run silently writes prediction runs into the project tree unless overridden, which is a sharp edge worth fixing now.
Fix: build the ADR-23 v2 object-store / table-native store (and unblock the live-Snowflake verification); change the default root to an explicit, absolute, non-project location.

### F21 The source-quality surface a data engineer expects is thin [DE - Med - M]

There is no source freshness gate (the scaffold `scheduled_retrain.yml` even concedes "freshness arrives as new snapshots", so a scheduled retrain has no upstream-is-stale guard), no row-count / volume anomaly gate, no `accepted_values`, and no `relationships`.
Checks also run post-materialization on the built splits (`quality/checks.py:100-104`), not on sources pre-join, so they cannot police source integrity before the fan-out of F2 happens.
The temporal label join is exact-equality on `time_column + offset` (`local/data.py:288`, `snowflake/sql.py:124`, `spark/data.py:266`) with no coverage report, so if label timestamps drift off the offset grid the rows drop silently through the inner join and the data engineer learns of it only via a bare "split materialized 0 rows", or not at all if 90% drop.
Fix: add `unique`/`relationships`/`accepted_values` checks (shared with F2), an optional source-freshness gate, and a label-join coverage statistic (spine N matched M, warn below a threshold).

### F22 Concurrent in-process dataset builds each grab all cores and 80% of RAM, uncoordinated [DE - Med-Low - S]

`build_dataset` runs inside the scheduler's thread pool and each call does a bare `duckdb.connect()` with no config (`local/data.py:197`), whose measured defaults are `threads = all cores`, `memory_limit = 80% RAM`, and `temp_directory = '.tmp'`.
So N parallel large builds at a high `--threads` each independently claim all cores and 80% of RAM with no coordination, oversubscribing CPU N-fold and risking an aggregate memory budget that exceeds physical RAM before any single connection decides to spill; and because the coordinator has chdir'd to the project dir, spills litter `<project-dir>/.tmp` and can fill a constrained CI disk.
Fix: configure each connection from mbt's own budget (`PRAGMA threads = max(1, cores // parallel_builds)`, a divided `memory_limit`, an absolute scratch `temp_directory`).

### F23 `format: iceberg` is accepted and documented but implemented nowhere [DE - Med - S]

`source.format` is a free `str` defaulting to `"parquet"` with a comment `# parquet | iceberg` (`specs.py:60`), but no adapter reads iceberg: local always `read_parquet` (`data.py:257`), Snowflake ignores it, and Spark implements `"delta"` (undocumented) rather than the documented `"iceberg"` (`spark/data.py:120`).
So a data engineer who sets `format: iceberg` gets silently-wrong behavior or a confusing engine error, and the one extra format that works is not in the spec vocabulary.
Fix: make `format` a validated `Literal`, reject formats the resolved adapter cannot read with an actionable error, and align the comment and docs with reality (delta on Spark today, iceberg is roadmap).

## P2 - adapters and cross-adapter parity

### F24 Spark categorical is ordinal encoding, not native categorical, and is mislabeled as parity [DS / DE - Med - M]

The StringIndexer fix removed the raw JVM crash (a real improvement), but the result diverges from the other three adapters: Spark feeds frequency-ranked ordinal codes as numeric into `VectorAssembler`, so the GBT does threshold splits on an arbitrary code (`spark/training.py:179-185,225-226`), whereas xgboost/lightgbm/h2o do true unordered-categorical partition splits via the shared `encoding.py`.
So a string feature produces a materially different model family on Spark, yet the capability matrix files this under "native categorical features: Y (indexed)" and the repo's own `revenue_demo` note documents ordinal-vs-native swinging r2 from 0.55 to 0.949.
The metric engine is shared, so metrics are computed identically, but the feature representation is not, so "same spec, different adapter, apples-to-apples champion/challenger" does not hold for categorical-heavy datasets with Spark as champion or challenger.
Fix: relabel the matrix cell ("ordinal-indexed, not native"), add a parity caveat to the Spark README and spec-reference, or offer a native-categorical Spark path.

### F25 The compliance suite, the contract's ship bar, has zero categorical and zero optional-capability coverage [platform - Med - M] (the structural fix behind F24)

`tiny_binary_dataset`/`tiny_regression_dataset` are all-numeric (`compliance/suite.py:61-121`), so although every adapter genuinely subclasses `TrainingAdapterCompliance`, the suite never exercises a string feature, which is exactly where cross-adapter parity diverges (F24), and it has no test for the recently-added optional capabilities (no calibration round-trip, no `train_with_report`, no `shap_importance`, no `explain`).
So a categorical-encoding regression, or a new adapter's broken categorical or calibration path, passes the "correct by construction" bar.
This is the one structural change that would have caught a whole class of the sweep's bugs, so it is worth more than its Med rating suggests.
Fix: add a mixed-type fixture plus a cross-adapter categorical-parity assertion, and compliance probes for each optional capability.

### F26 The adapter-authoring doc omits two must-know capabilities [ecosystem - Med - S]

`docs/adapter-authoring.md` documents `feature_importance`/`shap_importance`/`train_with_report` but never mentions `explain` or `supports_calibration`, yet core hard-errors when a scoring node sets `explain_top_k` and the adapter lacks `explain` (`job.py:947`), and the parser rejects any `calibration:` spec unless the adapter sets `supports_calibration=True` (`project_parser.py:579`).
A third party building strictly to the doc, the whole point of the "extensibility proof", ships an adapter that hard-fails those two user-facing features.
Fix: add `explain` and the `supports_calibration` plus fit-on-validation / persist / apply pattern to the contract table.

### F27 The optional-capability protocols are inert, and the docs overstate the guarantee [platform - Low-Med - S]

`SupportsTrainWithReport`/`SupportsFeatureImportance` are `@runtime_checkable` (`protocols.py:189,210`), but core probes every optional capability with `hasattr`, never `isinstance`, no adapter is statically annotated as either protocol, and there is no protocol at all for `shap_importance`/`explain`, so mypy never checks conformance.
The docstring claims the protocol "pins the signature so adapters cannot drift apart", but `runtime_checkable` checks attribute names only, not signatures, and nothing calls it, so the guarantee is decorative.
Fix: add typed conformance variables or `isinstance` assertions in the suite, and add protocols for the SHAP capabilities.

## Strategic recommendations

These are the moves that change the trajectory, not just the tree.

1. **Freeze v0.1 scope and ship it.**
The single highest-value action in the repo is not a feature; it is the tag, the PyPI publish, and one dogfooded model.
v0.1 was "a tabular vertical done extremely well", and it has since absorbed Snowflake, Spark, H2O, batch scoring, ground-truth monitoring, a 19-service showcase, calibration, walk-forward / k-fold / nested CV, SHAP/PDP, and fairness gates, all filed under "post-v0.1-scope".
The breadth is impressive, but nothing here has met real, messy data or a data scientist who did not write the example, and G1 (adoption) is still "ready for dogfooding" with zero real models.
Stop adding verticals until one real model and one real user have run the loop.

2. **Change the development driver from "close the finding" to "dogfood plus cross-feature tests."**
Every confirmed bug in this review lives in a feature combination or a real user path that no single finding named: a duplicated feature row, a crashed monitor, a pinned-manifest scorer, a calibrated backtest, a standalone install.
A review-driven loop cannot find these, because a finding names one vector; only combinations and real usage do.

3. **Make the compliance suite the ship bar it claims to be (F25).**
Mixed-type fixtures, optional-capability probes, and a cross-adapter parity assertion are the one structural change that would have caught F5, F7, F24, and the next parity regression before it shipped.

4. **Treat the showcase as a separate, pinned artifact, not part of the core review loop.**
Nineteen compose services, roughly 2,000 lines of bespoke glue, and about ten pinned upstream workarounds is a drift machine, and it drifted again between the resync and this review.
Pin it, test it on its own cadence, and keep it out of the surface that every core change has to carry.

5. **Give the data-engineering perspective first-class weight.**
Data contracts (`unique`/`relationships`/freshness, F2/F21), warehouse-native prediction sinks (F20), and portable split hashing (F19) are where "dbt for ML" is still a promise rather than a delivery, and they are the gaps a data engineer hits first, precisely because both prior reviews were written mostly through a DS and MLOps lens.

## What is genuinely solid (do not touch)

- The coordinator / job split and the compute seam: `_SUCCESS` and result-file completeness markers, the watchdog SIGTERM-then-SIGKILL grace, result-file-over-terminated ordering, and the public `parse_job_line`/`result_path_for` seam that remote adapters reuse.
- The identity model: the two-hash scheme, windows-as-expressions against a single anchor, the targeted plus freeze env digests, and `manifest_hash` volatile-field blanking that makes same-anchor compiles byte-identical; the state diff and its transitivity are correct.
- Metric parity by construction: every adapter's `evaluate` routes through the shared `evaluate_split`, so the numbers are computed identically; the parity issues in this review are upstream feature representation (F24) and data-split membership (F19), not the metric engine.
- The champion gate: a genuinely paired, direction-aware, degenerate-resample-safe bootstrap with a clean seed ladder (+1 tuning, +2 carve, +3 bootstrap, +4 folds).
- Secret hygiene: `env_var()`-only resolution, taint and redaction on every serialization path including the CLI catch-all, and env-var names (not values) crossing the job wire.
- Scheduler concurrency and the exit-code taxonomy: shared state mutated only under lock, race-free fail-fast cancellation, and a clean 0/1/2 split that never conflates a hard error with a quality failure.
- Test quality: real frameworks over mocks, explicit anti-tautology guards, byte-compared golden manifests that normalize only machine-dependent fields, and honestly-qualified coverage scope.
- The recently-landed features that are real and correct where they run: calibration's fit/persist/round-trip/apply on all four adapters (only Spark's packaging and the backtest combination break it), JVM regression dispatch, xgboost/lightgbm exact determinism, the Optuna sampler choice, `mbt rollback`, and `mbt predictions ls/show`.
