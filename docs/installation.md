# Installation

mbt is a set of Python packages: one engine (`mbt-core`), one contract layer every adapter builds on (`mbt-adapter-base`), and one package per integration.
You install the engine plus the adapters your project names in `profiles.yml` and in its model specs.

## Requirements

| Requirement | Version | Needed for |
|---|---|---|
| Python | 3.11, 3.12, 3.13, or 3.14 (all four run in CI) | everything |
| Java | 17 | only the JVM adapters: `mbt-spark` and `mbt-h2o` |
| git | any recent | installing from a release tag (below), and the scaffold's state-branch scripts |

## Choose an install path

!!! note "mbt is not on PyPI yet"
    The v0.1.0 release is published as a GitHub release with wheels attached, and PyPI publication is pending.
    Until it lands, install from a release tag or from a source checkout.
    Once it does, every command below becomes a plain `pip install mbt-core mbt-xgboost mbt-mlflow`.

### From a release tag (projects and CI)

This is what a project generated by `mbt init` does in CI.
Pin every mbt package you use to the same tag, **including `mbt-adapter-base`**: the other packages depend on it, it is not on PyPI either, and pip can only resolve it from a reference you give it.

```bash
pip install \
  "mbt-adapter-base @ git+https://github.com/satrijandi/mbt@v0.1.0#subdirectory=packages/mbt-adapter-base" \
  "mbt-core @ git+https://github.com/satrijandi/mbt@v0.1.0#subdirectory=packages/mbt-core" \
  "mbt-xgboost @ git+https://github.com/satrijandi/mbt@v0.1.0#subdirectory=packages/mbt-xgboost" \
  "mbt-mlflow @ git+https://github.com/satrijandi/mbt@v0.1.0#subdirectory=packages/mbt-mlflow"
```

Leave out the `mbt-adapter-base` line and pip stops with `No matching distribution found for mbt-adapter-base<0.2,>=0.1.0`.

A tag can be moved on GitHub.
Where that matters, replace `@v0.1.0` with the commit SHA it points at; a SHA is immutable.

### From a source checkout (trying mbt, contributing)

```bash
git clone https://github.com/satrijandi/mbt && cd mbt
uv sync                        # every package, plus the dev tools
source .venv/bin/activate      # puts `mbt` on PATH
```

This installs every adapter, including the JVM ones, so it is the quickest way to follow the [Quickstart](quickstart.md) or the [Tutorial](tutorial.md).
It is also the development setup described in [CONTRIBUTING](https://github.com/satrijandi/mbt/blob/main/CONTRIBUTING.md).

## Pick your packages

A project needs `mbt-core` and one adapter for each role its targets and specs name.
The scaffold's default (`mbt init`) uses the local data and compute adapters that ship inside `mbt-core`, plus XGBoost and MLflow.

| Role | Package | Adapter name in YAML |
|---|---|---|
| Engine and CLI | `mbt-core` | `local` (data and compute) |
| Contract layer | `mbt-adapter-base` | - (a dependency of every other package) |
| Training | `mbt-xgboost` | `xgboost` |
| Training | `mbt-lightgbm` | `lightgbm` |
| Training | `mbt-sklearn` | `sklearn` |
| Training | `mbt-h2o` | `h2o_automl` |
| Training, data, compute | `mbt-spark` | `spark` |
| Data | `mbt-snowflake` | `snowflake` |
| Tracking and registry | `mbt-mlflow` | `mlflow` |
| Tuning | `mbt-optuna` | `optuna` |
| Drift report engine | `mbt-evidently` | `evidently` (under `evaluation.report.stability.engine`) |
| Testing your project | `mbt-testing` | `fake` |

[Adapters](adapters.md) compares what each one supports.

### Optional extras

| Extra | Adds |
|---|---|
| `mbt-core[s3]` | `s3://` artifact stores (boto3) |
| `mbt-core[otel]` | OpenTelemetry spans, enabled with `MBT_OTEL=1` (see the [CLI reference](cli-reference.md#environment-variables)) |
| `mbt-snowflake[sso]` | Keyring-backed caching of the browser-SSO token, so `authenticator: externalbrowser` prompts once per session instead of once per job |
| `mbt-h2o[sparkling]` | The Sparkling Water backend, which trains H2O AutoML on Spark executors. It pins pyspark 3.5, so it cannot share an environment with `mbt-spark` (Spark 4) |
| `mbt-xgboost[onnx]` | ONNX export for programmatic callers of the adapter. `mbt build` always stores the native format |
| `mbt-adapter-base[compliance]` | The adapter compliance test suite, for [adapter authors](adapter-authoring.md) |

Extras attach to the same reference form, for example `"mbt-core[s3] @ git+https://github.com/satrijandi/mbt@v0.1.0#subdirectory=packages/mbt-core"`.

## Verify the install

```bash
mbt --version        # prints: mbt 0.1.0
mbt init demo && cd demo
python scripts/generate_sample_data.py
mbt parse            # exits 0: specs valid, adapters importable
```

`mbt parse` imports every adapter a spec names, so a missing package fails here with the adapter's name rather than halfway through a build.

## Keep a project's environment pinned

A compiled manifest records the environment it was built in (ADR-19), and `mbt run --manifest` refuses to execute in a different one.
A floating environment therefore breaks reproducibility, not just builds.

- The `requirements.txt` that `mbt init` writes pins the mbt packages to the release tag and the numerics stack (numpy, scipy, pandas, pyarrow, scikit-learn, duckdb, xgboost, mlflow) to the exact versions the scaffolding environment was running.
  CI installs from it, never from bare package names.
- `packages.yml` lists the adapter packages the project needs; `mbt deps` installs them, preferring the pinned `requirements.txt` when it exists, and verifies the result either way.

## Shell completion

```bash
mbt --install-completion     # bash, zsh, fish, or PowerShell; restart the shell afterwards
```

## Upgrading

Read the [changelog](https://github.com/satrijandi/mbt/blob/main/CHANGELOG.md) before upgrading a project with expensive models.
Every release states its **retraining impact**: mbt hashes the whole spec, so a release that adds a spec field changes every config hash, and the next `state:modified` build retrains everything (ADR-7).
Upgrade in its own PR, so that retrain is visible and deliberate rather than riding along with a model change.
